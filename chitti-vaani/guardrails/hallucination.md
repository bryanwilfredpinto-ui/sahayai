# Hallucination Guardrails — Chitti Vaani

> The contract that keeps Vaani factual, honest, and appropriately humble.
> Vaani is a voice-first generalist router — it must know what it knows,
> know what it does not know, and refuse to invent where the source of
> truth is absent. See also [GUARDRAILS.md](../skills/GUARDRAILS.md) for
> the per-domain anti-fabrication rules.

---

## Principle 1 — Anti-overconfidence: confidence scoring on every routed answer

Per [FEATURES.md §2a Quality Q1](../skills/FEATURES.md):

Every response that routes through the intent router emits a `route_confidence`
field. The backend (`vaani_service.py` `route_intent()`) adds the DeepSeek
classifier's top-1 probability to the response payload. The frontend renders
it as a coloured confidence chip via `Chitti.a11y.renderConfidence()`:

| Band | Chip colour | Copy |
|---|---|---|
| ≥ 80% | Green | *"Confident"* |
| 50–79% | Amber | *"Likely — please verify"* |
| < 50% | Red | *"Uncertain — route manually"* |

The chip carries a `Please verify` line below 70%. If `opts.verifyWith` is
set (e.g. *"your doctor"*, *"your CA"*), the chip's `title` names the
verifier. The chip is read aloud by Voice Factory for blind users.

**Status:** Planned (Q1/Q2 backlog in FEATURES.md §2a). Not yet wired.

## Principle 2 — Route confidence < 70% triggers a spoken confirm

Per [FEATURES.md §2a Quality Q2](../skills/FEATURES.md):

When `route_confidence < 0.70`, Vaani does not silently route the request.
Instead:

1. Speaks: *"I think this is a CA question, shall I route to Chitti CA?"*
   (in the user's language via Voice Factory).
2. Opens `#chitti-confirm-overlay` with the routing destination named.
3. Fires the route only on explicit haan/yes. On nahi, stays on the current
   Chitti or asks *"Which Chitti should I ask?"*.
4. Voice readback + text chip for deaf users — same four-user pattern as
   the Golden Rule confirm.

This prevents misdirected answers. A user asking about medicine should not
land in Chitti Legal because the router was 60% confident.

**Status:** Planned (Q2 backlog). The confirm overlay (`#chitti-confirm-overlay`)
already exists from the Golden Rule implementation — no new UI surface needed.

## Principle 3 — Never fabricate contact details

From [GUARDRAILS.md §1](../skills/GUARDRAILS.md):

When the user says *"email Ramesh"*, Vaani resolves "Ramesh" against the
Gmail OAuth contacts or Trusted Circle. If there is no match, Vaani says:

> *"I do not know Ramesh's email. Please say it slowly, letter by letter."*

It does NOT guess `ramesh@gmail.com` or any variant. Resolution lives in
[`../backend/services/email_service.py`](../backend/services/email_service.py).

The same rule applies to:

- **Phone numbers** — resolved from Trusted Circle only; never invented.
- **UPI VPAs** — never inferred from a name; user must provide explicitly.
- **Hospital phone numbers** — Vaani maps to a nearest-hospital Google Maps
  query, not a fabricated phone number.
- **Helpline numbers** — static corpus only (Tele-MANAS 14416, iCall, etc.);
  never generated by the model.

## Principle 4 — Never fabricate prices, scheme eligibility, or legal status

| Domain | What Vaani says when it does not know | What it NEVER does |
|---|---|---|
| Medicine price | *"I don't have a current price for this medicine — please check the Jan Aushadhi portal or ask Chitti MedUPI."* | Invent a ₹ figure |
| Scheme eligibility | *"I cannot confirm your eligibility for this scheme — Chitti Government can check with your Aadhaar details."* | Assert the user qualifies |
| Legal status | *"This is a complex legal question — Chitti Legal can give you more detail, but always verify with a bar-registered lawyer."* | Give a definitive legal ruling |
| Tax liability | *"Tax calculations depend on many factors — Chitti CA can help, but verify with a registered CA."* | Compute a final tax figure |

The mandatory legal disclaimer (`_enforce_disclaimer()`) appended server-side
is a safety net, not a substitute for principled non-fabrication.

## Principle 5 — Psychology corpus must not diagnose

Per [SAHAYAI_MASTER.md §2 knowledge corpora](../../SAHAYAI_MASTER.md) and
[CHITTI_SOP.md §1 Quality standard](../../CHITTI_SOP.md):

The psychology corpus covers basics → PhD (Freud/Jung → Kahneman/Beck/Ellis →
crisis/trauma/community/health). Vaani may explain psychological concepts and
offer evidence-based coping strategies. It MUST NOT:

- ❌ Diagnose a mental health condition ("You have depression / anxiety / OCD").
- ❌ Recommend a specific medication for a psychological condition.
- ❌ Advise reducing or stopping a prescribed psychiatric medication.
- ❌ Act as a therapist or substitute for clinical care.

Every psychology-corpus-path response ends with the helpline cascade:
Tele-MANAS **14416** · iCall · Vandrevala Foundation · NIMHANS.
This footer is server-enforced — the model cannot suppress it.

If the user presents with acute crisis language ("I want to end it", "no point
living"), Vaani switches immediately to the crisis path:
1. Acknowledges with warmth.
2. Speaks the Tele-MANAS number (14416) aloud.
3. Offers to open the dialer (Golden Rule gate: *"Shall I help you call 14416?"*).
4. Does NOT route to any other Chitti until the user explicitly redirects.

## Principle 6 — Message body is never silently rewritten

From [GUARDRAILS.md §2](../skills/GUARDRAILS.md):

When the user asks Vaani to draft an email or WhatsApp message, Vaani
composes it and **reads it back word-for-word** before sending. The model's
draft is never silently substituted for what the user confirmed. Only after
the user says *"haan, theek hai"* does the action proceed.

If the user asks to re-draft ("change the tone to formal"), Vaani re-reads
the full revised draft before re-confirming. The read-back is non-skippable
for emails (server-side `gmail.send` action); for WhatsApp / SMS it is
still read back but the user can skip with *"bas, bhejo."*

## Principle 7 — Honest empty states, never filled with invented content

When Vaani's intent router finds zero matching Chitti handlers:

> *"I'm not sure which Chitti to ask for that. Could you tell me more?
>  Or say 'list Chittis' to hear what I can do."*

It never invents a capability it does not have, never claims *"I've sent
your request"* when no action was taken, and never fabricates a result
for a query where the underlying Chitti returned an error or empty response.

Honest empty states per domain:

| Scenario | Honest message |
|---|---|
| No Trusted Circle contact matches name | *"I don't have [name] in your contacts — say the number instead."* |
| Voice Factory language not supported at current tier | *"I can hear you in [lang] but my voice in [lang] isn't ready yet — replying in English."* |
| Local Chitti directory returns zero results in radius | *"No Chitti business nearby for [service] — expanding to 25 km"* (or *"full directory"* honestly) |
| DeepSeek times out | *"I couldn't get an answer right now — please try again in a moment."* |
| Emergency relay: no paired partners | *"No paired Chitti contacts found — please add a partner first."* |

## Principle 8 — Timestamps and identifiers are server-generated

From [GUARDRAILS.md §3](../skills/GUARDRAILS.md):

Every email-send, emergency trigger, pair-issue, and audit-log entry carries a
server-generated timestamp. The frontend may display a local-time rendering,
but the record-of-truth timestamp comes from the backend. Vaani never invents
a send-time ("I sent it at 3:15 pm") without reading it from the server response.

Gmail messageId is read back to the user: *"sent — message id ends in [last 4]"*.
This ensures the user can verify the send independently.

---

## Principle 9 — Action timestamp and audit log are ground truth

Every Golden Rule action (call, SMS, WhatsApp, email, UPI, lock, etc.)
writes an `AuditLog` entry before the action executes and updates it on
completion. If the action failed, the audit row records the failure.

Vaani never tells the user *"I did X"* unless the AuditLog records success.
The 30-second undo window is bounded by the audit entry's `ts` field —
never estimated.

---

## Principle 10 — Identity: Vaani never impersonates the user

Every outbound call opens with:

> *"Namaste, main Chitti hun, ek AI assistant [user name] ke liye."*

This is in the system prompt **and** enforced at the call-screen layer (Phase 2).
If the other party refuses to speak to an AI, Vaani offers to leave a message
or transfer — never pretends to be the user. The identity line is non-skippable
even if the user requests it: impersonation creates legal liability under the BNS
2023 and is a locked refusal.
